# 依赖全景（5 层）数据库压力评估

- 日期：2026-10-29
- 环境：本机 Demo，PostgreSQL 15.19 容器，8 核 / 24 GB，未设置容器 CPU 限额，`shared_buffers=128MB`
- 评估对象：`GET /v1/jobs/{id}/dependency-graph?depth=5` 的 Store 查询
- 结论：**在真实人工浏览频率下压力很小；即使是最坏形态的图，5 层查询也已被节点上限约束在毫秒级。** 生产风险不在 5 层本身，而在无上限的递归 CTE 形态；该形态已改为逐层 BFS。

## 1. 测试数据

单独使用 `sched_graphbench` 数据库，不污染 Demo/测试库：

- 200,000 jobs
- 200,000 job versions
- 500,000 runs（`run` 表总大小 259 MB）
- 每任务 2–3 条历史运行，最新运行可被节点详情查询命中

三种依赖拓扑：

| 场景 | 节点 / 边 | 说明 |
|---|---:|---|
| 链 | 6 / 5 | 最小深度控制 |
| 4 叉 5 层树 | 1,365 / 1,364 | 普通多层图 |
| 宽扇出最坏形态 | 200,000 / 199,998 | 根 500 个下游，下一层约 20 万个下游；5 层可达 |
| 密集前沿 | 30,121 / 30,120 | 第 2 层 60 个节点各有 500 个下游，专门压每层前沿查询 |

宽扇出图超过了 UI 的 200 节点上限，用于验证“先截断、再停止遍历”，而不是把整张图拉回内存。

## 2. 方法

- 直接调用生产代码的 `Store.GetDependencyGraph`（pgxpool），不经过 HTTP/Auth，因此统计的是数据库与查询开销，页面总延迟只多 API 和网络几毫秒。
- 每个场景先做 5 次预热，再顺序执行 2,000 次，统计 p50/p95/p99、QPS。
- 压测窗口前后读取 `pg_stat_database`（事务、共享块、临时文件），并用 `docker stats` 采样 PostgreSQL 容器 CPU。
- 对照：同一个宽扇出图用改造前的递归 CTE 查询。

## 3. 结果

### 3.1 BFS（当前实现）

本机为共享环境，重复测量的 p50 有约 2 倍抖动；下表采用较慢观测值，结论按保守值计算。

| 场景 | p50 | p95 | p99 | max | 单连接 QPS |
|---|---:|---:|---:|---:|---:|
| 6 节点链（中部任务） | 1.1ms | 1.3ms | 1.7ms | 4.1ms | 894 |
| 1,365 节点 4 叉树（5 层） | 2.4ms | 2.7ms | 2.9ms | 14.9ms | 406 |
| 200,000 节点宽扇出（5 层） | 4.2–5.6ms | 7.9–8.2ms | 9.8–10.3ms | 25.8ms | 171–231 |
| 密集前沿（30k 边/层，5 层） | 2.4–7.3ms | 2.6–10.5ms | 3.3–12.8ms | 36.1ms | 137–419 |

宽扇出图在 200 节点处截断；图中不再返回 20 万节点的中间结果。

### 3.2 数据库侧增量

- 宽扇出，2,000 次：
  - `xact_commit` +6,021（3.01 次/请求）
  - `blks_hit` +2,852,190（1,426 块/请求）
  - `blks_read` +19
  - `temp_bytes` 无增长
  - PostgreSQL 容器 CPU 采样约 **41%–53%**（对应约 231 请求/s，采样期间有共享环境抖动）
- 4 叉树，2,000 次：
  - `xact_commit` +12,036（6.02 次/请求）
  - `blks_hit` +3,050,699（1,525 块/请求）
  - `temp_bytes` 无增长
  - CPU 采样约 **37%**（对应约 389 请求/s）
- 密集前沿，2,000 次：
  - 观测到约 137–419 请求/s、CPU **40%–45%**
  - 单请求 p50 2.4–7.3ms、p99 3.3–12.8ms；仍无临时文件增长
  - 这是测到的最重单页形态，来源是每层前沿 30k 条候选边，而不是节点总数

查询次数随图的“实际层数”增长，而不是随可达节点总数增长；宽图虽然数据库里约有二十万条边，达到 200 节点上限后只执行 2 次边查询 + 1 次节点详情查询。

### 3.3 4 并发页面

宽扇出图、4 个并发客户端、4,000 次：

```text
qps=1253.6  p50=3.1ms  p95=4.0ms  p99=4.8ms  max=14ms
PostgreSQL CPU 采样：156%（容器未限核，约 1.56 核）
```

并发时吞吐线性扩展，没有锁等待；按这个采样，1 页/s 的数据库 CPU 约 0.12%，100 页/s 约 12%。生产页面是人工打开，没有自动刷新，距离这个量级很远。

### 3.4 改造前递归 CTE 对照

同一宽扇出图（depth=5）：

```text
Execution Time: 1505.599 ms
Buffers: shared hit=599502, temp read=731 written=1463
```

递归 CTE 会先把约 20 万个可达节点全部物化，最后才应用 `LIMIT 201`；一次页面查询即可消耗秒级 DB 时间和数百 MB 缓存流量。改为 BFS 后同一查询 p50 约 4–6ms（本机保守观测），p99 约 10ms。

## 4. 按页面访问量外推

以宽图较慢观测的约 47% / 231 QPS 线性外推，且不计 API/网络：

| 依赖页访问量 | 估算 PostgreSQL CPU |
|---:|---:|
| 1 页/s | 约 0.20% |
| 10 页/s | 约 2.0% |
| 100 页/s | 约 20% |

密集前沿按约 44% / 188 QPS 外推：1 页/s 约 0.23%，10 页/s 约 2.3%，100 页/s 约 23%。这是更保守的页面形态。

4 叉树形态约 37% / 389 QPS，1 页/s 约 0.10%；仍远低于此前 58 run/s 业务压测的 19%。当前页面没有自动刷新，只有打开页面、切换层数和手动刷新会查询。

## 5. 结论与限制

- 5 层、200 节点上限下，常见图形单次查询 p99 约 3–5ms；宽图/密集前沿 p99 约 10–13ms。人工访问频率下 DB CPU 可忽略。
- 真正的保护来自“逐层查询 + 每层 LIMIT + 200 节点停”，而不是单纯把 depth 从 3 改成 5。
- 压测是本机热缓存、无并发调度/Worker 写入的合成环境；生产冷启动会增加少量 I/O，但 200 个节点的索引查找仍有界。
- 若未来把依赖页做成秒级自动轮询或开放给大量机器人访问，应加短 TTL 缓存/ETag，并继续监控 `pg_stat_database.temp_bytes` 与 p99；按当前实现，100 页/s 的 CPU 仍有余量。
