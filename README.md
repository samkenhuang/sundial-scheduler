> 日晷不制造时间，只让时间可见。

调度系统最好的状态，是让人忘记它的存在。

Sundial 是一个面向大规模作业的调度平台。它保留了 Jenkins 时代最好的那部分——一眼能看懂的任务、可追溯的历史、可以放心重跑的构建；同时把底层换成更安静、更克制的现代控制面。

它不试图成为万能平台。它只做好一件事：在正确的时间，把正确的任务，交给正确的执行器，并留下清楚的记录。

## 它是什么

在 Sundial 里，任务不是一堆配置，而是一条有时间感的工作流。版本、参数、Cron、手动触发与依赖关系，最终都收敛为一次可以被观察的运行。

任务有版本，运行有历史。每次构建都知道自己从哪里来、由什么触发、在哪个执行器上发生。

依赖不是黑箱。上游为什么触发、下游为什么等待、一次运行卡在哪一层，都能在界面上找到答案，而不是靠翻日志猜测。

日志也不是事后附件。运行中的输出可以实时跟随，结束后的日志可以回看、下载、归档；来源、时间与执行器，都留在记录里。

## 设计信念

**确定性先于自动化。**

调度系统不应该制造惊喜。同样的输入，应该得到同样的路径；失败时，应该知道失败在哪里，而不是只看到一句“任务未完成”。

**界面是系统的一部分。**

如果一个状态只能从日志里猜出来，那它就不算被设计过。Sundial 的控制台不追求信息越少越好，而是让重要的信息在正确的层级上出现。

**失败必须可解释。**

运行可以失败，但失败不能模糊。取消、超时、执行器掉线、上游未就绪——每一种结束，都应该有清楚的归宿。

## 界面

控制台的气质，来自克制：密集但不拥挤，信息完整但不喧哗。它更像一张随时可以展开的工程图纸，而不是一块只会闪灯的仪表盘。

## 架构，克制到只剩三件事

| 角色 | 职责 |
| --- | --- |
| **控制面** | 记录事实：任务、版本、运行、日志与执行器状态。 |
| **调度器** | 只做决策：什么时候触发，谁还在，谁已经离开。 |
| **Worker** | 只负责执行：领一条运行，执行，上报。从不连接数据库。 |

PostgreSQL 记录意图与结果，Redis 只负责“呼吸”，Worker 只向外发起请求。控制面短暂不可用，不会杀死正在运行的任务。

没有中心化的任务派发，没有虚拟分片，也没有一台必须永远正确的 Master。每个角色都只做自己该做的事。

## 开始

需要 Go 1.23+、Node 22.12+ 和 Docker。

```bash
make db-up
make migrate
make web-build
make run-server
```

另开两个终端：

```bash
make run-scheduler
make run-worker
```

然后打开 <http://127.0.0.1:8080/ui/>。

当前为 P0/P1 实现，适合单租户、自托管场景。生产部署前，请先阅读部署文档中的边界说明。

## 为什么叫日晷

日晷不制造时间，只把时间变成可以阅读的影子。

好的调度系统也不制造忙碌。它让每一件事在正确的时间发生，然后安静地退到背景里。
